# 顾清影 语音功能: 唤醒、识别、听写与回复播报 (TTS)

> 本文档描述 顾清影 当前语音系统的完整架构与运行机制：安装使用、各部件职责、音频管线、TTS 播报、配置规范、排查与测试。
> 语音子系统涵盖 **唤醒 (KWS)**、**离线识别 (STT)**、**多端流式听写 (Dictation)** 与 **多源回复播报 (TTS)**，并在无语音活动时保持极低资源占用。

---

## 一、一句话概括

装上可选组件 `gqy-voice`，在配置或设置面板中启用「语音功能」：
- **语音唤醒**：喊「清影清影」（或自定义唤醒词） → 提示音 + 桌面通知「顾清影 在听」 → 给出指令 → 通知「顾清影 收到: …」 → **在终端那条会话里执行**（终端开着就实时渲染出来，跟手打的一轮一样；没开也照跑） → 执行完成触发提示音、桌面摘要通知并朗读回复。
- **快捷键唤醒**：桌面快捷键绑定 `gqy listen`，无需喊唤醒词直接进入收听状态；若正在收听或播报中，再按一次立即打断全停。
- **听写输入**：终端 REPL `/stt`、命令行 `gqy stt`、WebUI 麦克风按钮（WebSocket 流式）共享同一套离线 VAD/分句/识别管线。
- **回复播报 (TTS)**：支持 `<speak>` 标签优先朗读与 Markdown 正文清洗，集成 MiniMax 与 Xiaomi MiMo 双引擎，并支持 `speak` 工具让模型主动开口。

## 二、为什么拆分为两个可执行文件

| 维度 | `gqy` (主程序 / daemon) | `gqy-voice` (语音前端进程) |
|---|---|---|
| **链接依赖** | 不含 sherpa-onnx / onnxruntime（轻量运行） | 静态链接 sherpa-onnx（二进制 ≈ +30MB） |
| **音频硬件** | 不直接访问麦克风与扬声器底层 | 独占常驻麦克风流，负责播放提示音与 TTS WAV |
| **模型加载** | 零模型代码，不占 ASR 内存 | VAD 与 KWS 常驻（~80MB），SenseVoice 按需加载/超时自动卸载 |
| **未启用状态** | 零常驻线程、零音频内存开销 | 根本不会被拉起 |

主程序对语音的前端感知全部收敛于 [`src/web/voice_bridge.rs`](../src/web/voice_bridge.rs)：
- **进程看护**：自动定位二进制（同目录 → PATH 搜索）、崩溃指数退避重启、配置热重载重启、主程序退出时优雅清理。
- **信令交互**：通过一条持久 IPC 连接（`VoiceAttach`）进行双向事件交换。
- **会话调度**：驱动语音回合、通知分发、打断控制与听写中继。

```text
gqy (daemon) ───────spawn/supervise───────> gqy-voice
   voice_bridge  <───VoiceAttach 双向信令帧───>  voice::worker
   · voice.command{text} ──────> 终端 REPL 会话(job_wake 可见) ───> 通知 / TTS 播报 / cue(done)
   · voice.speech_start ───────> 打断当前正在进行的推理或播报
   · voice.listen ─────────────> 快捷键免唤醒直接收听 / 再次按下全停
   · voice.dictation{text} ────> 听写认领者 (REPL /stt、gqy stt)
   · voice.audio{pcm16} ───────> WebUI 浏览器录音经 WebSocket 转发 worker 识别
   · voice.play{wav_path} ─────> 交付 daemon 合成好的 TTS 音频进行物理播放
```

### 编译与打包契约
- **Cargo Feature**：主 crate 的 `voice` 特性默认关闭；`[[bin]] gqy-voice` 标记了 `required-features = ["voice"]`。
  - 仅构建主程序：`cargo build --release`（仅产出 `gqy`）。
  - 构建全套语音：`cargo build --release --features voice`（同时产出 `gqy` 与 `gqy-voice`）。
- **打包规范**：在 Arch Linux / AUR 中拆分为 `gqy` 与 `gqy-voice` 两个包；`sherpa-onnx` 静态库预先打包并校验哈希，构建期完全离线。

## 三、离线模型体系 (~190MB)

模型统一存放在 `state_dir/models/`（通常为 `~/.gqy/models/`，可通过环境变量 `GQY_VOICE_MODELS_DIR` 覆盖）：

| 模型 | 预估体积 | 职责说明 | 常驻策略 |
|---|---|---|---|
| **Silero VAD** (`silero_vad.onnx`) | 0.6MB | 语音活动检测，准确识别人声起止 | 能量门限之后常驻 |
| **KWS Zipformer** (wenetspeech 3.3M int8) | 31MB | 关键词唤醒小模型，专一识别唤醒词 | 常驻 |
| **SenseVoiceSmall** (zh-en-ja-ko-yue int8) | 156MB | 多语言非自回归语音识别（普通话、粤语、英语、日语、韩语） | 仅在有识别需求时加载，空闲按 `stt_unload_seconds` 释放 (~300MB) |

> 首次开启语音唤醒（`voice.enabled = true`）时，daemon 会自动从官方源下载解压缺失的模型文件，下载前后均会弹出桌面通知。

### 唤醒词灵活编码 (`keywords.rs`)

系统无需重新训练声学模型，通过解析 wenetspeech 的 `tokens.txt` 建模单元，动态将唤醒词转换为声母与带调韵母序列：

| 唤醒词书写方式 | 示例 | 内部处理机制 |
|---|---|---|
| **汉字** | `清影清影`、`顾清影` | 逐字注带调拼音，按 tokens.txt 贪婪最长匹配拆分为音节单元 |
| **显式拼音** | `qing1 ying3 qing1 ying3` | 空格分隔的“拼音+声调数字”（0 或无数字为轻声），精确控制读音 |
| **假名 / 拉丁字母** | `みゆみゆ`、`gqygqy` | 假名转罗马音，按日语音节切分后映射为近似发音，并自动展开为轻声与 1~4 声组合候选 |
| **混合形式** | `小gqy` | 汉字保持固定声调，外来词部分展开为多声调候选矩阵 |

- **灵敏度调节**：
  - `wake_threshold`（默认 `0.25`，越低越灵敏）：对应 sherpa 的关键词检出概率阈值。
  - `wake_boost`（默认 `1.0`，越大越灵敏）：对应关键词得分加权系数。
#### 声调要对得上（唤醒不灵先查这个）

KWS 的建模单元是**带调韵母**：`ǐng`（三声）和 `íng`（二声）是两个不同的 token。唤醒词编码出的序列和你嘴里出来的声调对不上，就**永远不会命中**，调再低的 `wake_threshold` 也没用——那不是灵敏度问题，是序列压根不匹配。

纯汉字唤醒词**只生成一行、一个固定声调**（`TONE_VARIANTS` 声调展开只对假名/拉丁字母生效）。所以书面读音和实际读音不一致的词要手动把变体补上。

09-16 实测的例子：「清影清影」注册的是 `q īng y ǐng q īng y ǐng`，但实际喊出来是二声——「清影」不是常用词，「轻盈」是，嘴会往高频词上滑。默认配置因此同时注册了 `qing1 ying3` 与 `qing1 ying2` 两种。

**排查顺序**（`gqy-voice test --keyword <词> --timings`）：

| 现象 | 结论 |
|---|---|
| 一行「听到 N 秒语音」都没有 | 音频没进来：查设备、麦克风权限 |
| 有「听到语音」但从不命中 | 唤醒词层。换个声调稳的词（如「宝宝」）试：能中就是声调/编码问题，不中才往音频质量上查 |
| 换词能中、原词不中 | 声调对不上。用 `gqy stt` 或唤醒后的识别结果看**它到底把你听成了什么**，按那个读音补一条显式拼音唤醒词 |

显式拼音写法是空格分隔的「拼音+声调数字」（0 或无数字为轻声），任一唤醒词命中即唤醒。

- **500ms 段前音频补偿 (Pre-roll)**：
  由于能量门和 VAD 判定人声起音通常存在微小延迟，容易切掉弱起音声母（如 m / n / b 开头的词首）。音频管线维护一个 23 秒的环形缓冲区，在 VAD 判定语音段成立时，向前补回 500ms 原始音频再送给 KWS 与 STT，大幅提升检出率。

## 四、音频管线与低功耗设计 (`src/voice/pipeline.rs`)

```text
麦克风采集 (16kHz Mono f32)
   │
   ▼
[自适应能量门 (EnergyGate)] ───(安静环境下直接跳过 VAD 计算，CPU 近乎为 0)
   │
   ▼
[Silero VAD 句子切分] ────(结合 500ms 段前音频回填)
   │
   ├─► [Idle 待唤醒态] ───► 整段送 KWS ───► 命中即刻上报 Wake 提示音 ───► 同段送 STT
   │
   └─► [Window 免唤醒/听写态] ───► 整段送 STT ───► 提取指令或听写文字
```

1. **自适应能量门**：
   实时跟踪环境噪声底（RMS），当音频能量低于 `噪声底 × 2.5` 且小于绝对下限 `-54dBFS` 时，不送入 VAD 模型计算。在安静房间内麦克风常开状态下，前端 CPU 占用仅约 0.4%。
2. **KWS 整段判定**：
   日常人机对话中唤醒词与指令往往连贯说出（例如“清影清影帮我看看天气”）。等待 VAD 切出完整分句后再整体识别，避免逐帧流式推演浪费算力。
3. **唤醒反馈零等待**：
   KWS 一旦判定唤醒词命中，立即向系统发射 `voice.wake` 信令鸣响提示音并弹窗，随后异步加载或执行 STT 转写，避免冷启动加载模型的 1~2 秒阻塞用户的听觉反馈。
4. **STT 内存自动卸载**：
   在会话结束或免唤醒窗口关闭后，若闲置达到 `stt_unload_seconds`（默认 60 秒），自动卸载 SenseVoice 模型，释放约 300MB 物理内存。
5. **起势人声打断 (Barge-in)**：
   在免唤醒窗口中，若检测到持续 300ms 的人声（`SPEECH_START`），立即上报 `voice.speech_start`，主程序**切断扬声器播放，但不动正在跑的回合**——她在改文件时你插一句「等一下」，活不会白干。明确要停有两条路：说出新指令（`voice.command` 会取消上一轮），或按快捷键 `gqy listen`。

## 四·五、语音落在哪条会话

语音回合**不另开会话**，直接跑在终端那条 REPL 会话上（`ensure_repl_session`，固定走 normal 人格车道）。这条指针存在库里，终端关掉它也还在，所以：

| 场景 | 行为 |
|---|---|
| 终端开着 | 回合带 `job_wake` 标记，REPL 客户端发现后挂上实时渲染——语音这一轮和手打的那一轮长得一模一样 |
| 终端没开 | 回合照跑、TTS 照念，只是没人渲染；下次 `gqy` 进来历史都在，接着聊 |
| 多个终端 | 同一条会话，谁在前台谁看到 |

配套的两点：

- 喂给模型的是 `<voice_input>…</voice_input>` 包裹（语音协议要它才给 `<speak>` 口语版），但终端里显示的是**原话**——`display_content` 与 `content` 分开，用户不会读到一串尖括号。
- `gqy voice reset` 只清 09-16 之前那条专属语音会话的残留（kind=`voice`），**不碰当前会话**。要清当前对话用 `/reset`。

> 09-16 之前语音跑在一条专属 lane 里，于是终端里说过的话语音问不到，只能等记忆整理完靠联想撞运气。长期记忆本来就是按人格全局存的（不分会话），缺的一直是当轮上下文——会话一合并就没这问题了。

## 五、交互与控制规范

### 1. 提示音与桌面通知映射

| 触发事件 | 提示音效 (`assets/voice/`) | 桌面通知 |
|---|---|---|
| **唤醒词命中** | `wake.wav` (上行双音) | 「顾清影 在听 / 请讲」（与提示音同时呈现） |
| **识别出有效指令** | `heard.wav` (清脆单点音) | 「顾清影 收到 / <指令内容>」 |
| **指令执行完成** | `done.wav` (下行三音) | 「顾清影 / <回复前 N 字摘要>」(`notify_reply_chars`) |
| **手动关闭收听 (`gqy listen`)** | `off.wav` (下行双音) | 「顾清影 / 不听了」 |
| **执行异常失败** | `error.wav` (低沉警示音) | 「语音会话出错 / <错误详情>」 |

> 提示音内置于 `gqy-voice` 二进制中（木琴音色，24kHz mono）。Linux 系统下通知使用 `notify-send -p/-r` 机制，实现同一气泡的原地平滑替换，避免屏幕被多条通知轰炸。

### 2. 免唤醒追问与主动退下

- **免唤醒追问窗口 (`follow_up_seconds`, 默认 30 秒)**：
  - 计时**从 AI 回复播报完毕后才正式开始计算**（在模型推理中、TTS 合成中、音频播放中，计时均处于冻结状态）。
  - 用户在 30 秒内直接说话无需重复喊唤醒词；每次回合交互完毕后重新重置 30 秒窗口。
- **主动结束**：
  - 用户对她说“没事了”、“就降吧”、“去忙吧”等，模型将自动调用内置工具 `end_voice_chat` 关窗，回到待命状态。
- **快捷键开/关切换器 (`gqy listen`)**：
  - **待命时按下**：跳过唤醒词，直接发出提示音并进入 8 秒等待指令窗口。
  - **收听中/播报中按下**：彻底停止当前回合、打断 TTS 播放、销毁未播音频，并弹出「不听了」通知。
  - 推荐将其绑定到桌面环境快捷键（如 Niri、Hyprland、i3 等）。

### 3. 多端听写能力 (Dictation)

| 入口方式 | 音频输入源 | 识别文本流向与行为 |
|---|---|---|
| **终端 REPL `/stt`** | 本机麦克风 | 开启 10 秒静默短窗口（期间唤醒暂停），逐句填入终端输入框；回车发送，Esc 取消。 |
| **命令行 `gqy stt`** | 本机麦克风 | 录入单句指令，识别完成后直接提交为回合消息并流式打印回复（Shellhook 风格）。 |
| **WebUI 麦克风按钮** | 浏览器 `getUserMedia` | 前端通过 WebSocket (`/api/voice/stream`) 上传 16kHz PCM16 音频流，复用服务端的 VAD 与识别管线，逐句回传并在输入框中实时追加。 |

## 六、文本转语音 (TTS) 与平台语音生态

顾清影 提供独立的 `voice.tts` 配置节。文本转语音与语音唤醒相互独立（`voice.enabled` 控麦克风唤醒，`voice.tts.enabled` 控音频合成与朗读）。

### 1. 朗读内容提取与清洗规范

0. **分句流水线播报（09-16）**：
   整段合成要一到三秒，这期间是全静默的干等。现在按句末标点切一刀：第一句短、合得快，先出声；剩下的在它播的时候合成，接上排队播出。首声延迟从「整段合成」降到「第一句合成」。
   - 只切一刀，不逐句切碎——每段都是一次独立合成，接缝多了句子之间的语气断得明显。
   - 太短的开头（「好的。」）不单独成段，长到六十字还没标点也不硬切，两种情况都退回整段合成。
   - 前端 `Speaker` 相应改成**排队**播放：此前播放中送来的段会被直接丢弃。段与段之间 `speaking` 状态保持不抖（`voice.play` 带 `more` 标记 + 3 秒宽限期），否则管线会在接缝处恢复喂麦克风帧，把喇叭里的下一段当成用户开口，她自己把自己打断。

1. **`<speak>` 协议优先**：
   系统提示词中规范了模型输出行为。若模型在正文后附带 `<speak>口语化简短摘要</speak>`，TTS 仅朗读该标签内的文本，正文中的长篇代码与表格不会被冗长念出。
2. **正文自动清洗降级**：
   若模型未提供 `<speak>` 标签，系统会自动剔除代码块（整块丢弃）、行内反引号、Markdown 标题/列表符，并将超链接替换为“链接”、文件路径替换为“路径”，限制在 `max_chars`（默认 300 字）内平滑朗读。

### 2. 双供应商支持 (`voice.tts.active`)

- **MiniMax (`t2a_v2` 接口)**：
  - 支持 `speech-2.6-turbo`、`speech-2.8-hd` 等全系列模型。
  - 支持音色检索（WebUI / TUI 可直接拉取官方及克隆音色列表）。
  - 支持精细控制语速 (`speed`)、音量 (`vol`)、音调半音偏移 (`pitch`)、情感 (`emotion`) 与语种增强 (`language_boost`)。
- **Xiaomi MiMo (`chat/completions` 音频接口)**：
  - 模型：
    - `mimo-v2.5-tts`：使用官方预置音色（如 `冰糖`、`茉莉`、`苏打`、`白桦` 等）。
    - `mimo-v2.5-tts-voicedesign`：通过自然语言描述（`prompt`）实时生成指定音色。
    - `mimo-v2.5-tts-voiceclone`：指定本机音频文件（`sample_audio`，≤10MB）克隆目标音色。
  - 自然语言调音：MiMo 无数字语速参数，支持在 `prompt` 中通过口语描述（如“语速稍快，像跟朋友聊天一样”）直接驱动表现力。

### 3. 工具与通信平台整合

- **主动开口工具 (`speak`)**：
  在本地会话中注册，允许模型在需要主动向用户汇报进展时调用扬声器发声。
- **QQ 语音消息入站 (`voice_inbound.rs`)**：
  接收到群友或好友发送的 QQ 语音消息后，自动拉取 WAV 音频经本地 `gqy-voice` 转写为 `[语音] 转写内容`，使大模型能够理解语音输入。
- **QQ 语音消息出站 (`send_voice_message` / `send_qq_message`)**：
  将待回复文本经 TTS 引擎合成为音频后，作为 OneBot `record` 语音段发送，并在历史记录中完整保留 `[语音] 原文`。

## 八、常用排查与诊断命令

### 1. 运行状态检视
- **命令行状态**：`gqy voice status`（查看 worker 进程 PID、IPC 挂载状态、采集设备、日志文件路径等）。
- **REST 接口**：`GET /api/voice/status`（与 WebUI 共享同样的状态快照）。
- **进程日志**：查看 `~/.gqy/logs/voice-worker.log`（若需观察 VAD/KWS/STT 各阶段精细耗时，可添加环境变量 `GQY_VOICE_DEBUG=1`）。

### 2. 独立排查与硬件测试
当怀疑麦克风无声或唤醒词识别不灵敏时，可绕过主程序直接运行 `gqy-voice` 进行验证：
```bash
# 列出系统当前检测到的所有音频采集源 (源名与标签)
gqy-voice devices

# 独立运行唤醒与识别测试 (观察实时 RMS 能量门、VAD 状态与耗时)
gqy-voice test --keyword 清影清影 --timings

# 试听内置提示音 (wake / heard / done / error / off)
gqy-voice cue done --volume 0.8

# 测试 TTS 合成与扬声器回放
gqy voice say "你好，这是语音功能测试"
```

### 3. Linux PipeWire / WirePlumber 踩坑指南
- **声音静音或流串线问题**：
  如果出现提示音无声或唤醒失灵，检查 WirePlumber 是否错误记录了设备路由：
  ```bash
  grep gqy-voice ~/.local/state/wireplumber/stream-properties
  ```
  若发现带有 `"target"` 的条目，说明曾使用 pavucontrol 移动过该流，导致后续流被永久锁死。清理方式：停用 wireplumber 服务并清除上述配置文件中的 target 字段后重启。
- **USB 麦克风带宽瓶颈**：
  当多个 USB 高保真音频设备挂载于同一 USB Hub 时，麦克风常开可能导致带宽耗尽报错。建议将配置项 `voice.microphone` 显式指定为 `gqy-voice devices` 输出的真实物理设备名，避免跟随系统默认设备漂移。

## 九、性能基准与实测指标 (Release 模式，参考数据)

在安静工作环境下，测试 SenseVoiceSmall 与 KWS 的典型表现：

| 运行相位 | CPU 平均负载 | 内存常驻 (RSS) | 延迟 / 吞吐性能 |
|---|---|---|---|
| **安静待命态** (能量门生效) | **0.4% ~ 0.6%** | 约 75MB ~ 80MB | — |
| **KWS 唤醒词判定** (人声说话) | 短暂脉冲 (约 7%~9%) | 约 80MB | **60ms ~ 100ms** 完成全文检索 |
| **SenseVoice 首次加载** | 瞬时 CPU 脉冲 | 升至 380MB ~ 400MB | 约 1.2s ~ 2.0s 完成冷启动 |
| **SenseVoice 句子热识别** | 短暂脉冲 | 约 280MB (卸载前) | 3~5 秒语音识别仅需 **150ms ~ 300ms** |
| **空闲 60s 卸载后** | 回落至 **0.4%** | 回落至 **75MB** | 彻底回收 ~300MB ASR 模型内存 |

**总结**：
顾清影 语音系统的底层设计始终秉持低足迹与高响应：在无语音时近乎零开销，在唤醒触发瞬间毫秒级反馈，在交互结束后自动回收重型 ASR 内存，并无缝融合端侧离线识别与云端高品质 TTS 表现力。
